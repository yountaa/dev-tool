# Авторизация и доступ к вкладкам

Права выдаются **на модуль (вкладку) целиком**. Уровня окружения нет — решение
принято сознательно, дробить права тоньше не следует. Вся логика приложения
собрана в `backend/access.py` и не привязана к конкретному модулю.

---

## Цепочка запроса

```
браузер
  └─► внешний nginx (TLS)          — auth_request к oauth2-proxy
       └─► oauth2-proxy + Keycloak — логин, выдача заголовков
            └─► nginx фронта       — пробрасывает заголовки на API-пути
                 └─► backend       — читает личность и группы
```

Заголовки, которые проставляет oauth2-proxy:

| Заголовок | Переменная | Что несёт |
| --- | --- | --- |
| `X-Forwarded-Preferred-Username` | `AUTH_USER_HEADER` | имя пользователя (`preferred_username` из Keycloak) |
| `X-Forwarded-Groups` | `AUTH_GROUPS_HEADER` | список групп через запятую |

В Keycloak требуется **group membership mapper** в клиенте, иначе группы не
попадут в токен и до приложения не дойдут.

## Переменные

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `AUTH_ENABLED` | `false` | `true` — личность берётся из заголовка; `false` — прокси нет, автором действий становится `AUTH_FALLBACK_USER` |
| `AUTH_USER_HEADER` | `X-Forwarded-Preferred-Username` | заголовок с именем |
| `AUTH_FALLBACK_USER` | `local` | имя, когда авторизации нет |
| `AUTH_GROUPS_HEADER` | `X-Forwarded-Groups` | заголовок со списком групп |
| `RBAC_ENABLED` | `false` | `false` — всем видно всё |
| `access_<module>` | — | какие группы видят модуль |
| `RBAC_ADMIN_GROUP` | — | группы, которым видны все модули |

## Правила доступа

Логика в `access.can_access()`:

1. `RBAC_ENABLED=false` **или** `AUTH_ENABLED=false` → доступ не ограничивается;
2. пользователь состоит в одной из `RBAC_ADMIN_GROUP` → видит все модули;
3. у модуля нет своей `access_<module>` (или она пустая) → модуль виден всем;
4. `access_<module>=*` → модуль открыт **всем вошедшим**, включая пользователя
   без единой группы;
5. иначе нужна хотя бы одна совпадающая группа (логика OR).

```bash
RBAC_ENABLED=true
RBAC_ADMIN_GROUP=observability-admins,platform-admins   # несколько — через запятую
access_silences=team-oncall,team-sre                     # любая из групп
access_victoria=team-metrics
access_alerts=*                                          # открыт всем вошедшим
```

Значение `*` работает только в `access_<module>`. В `RBAC_ADMIN_GROUP`
перечисляются буквальные имена групп.

### Инвариант: RBAC работает только вместе с авторизацией

Без `AUTH_ENABLED=true` групп физически нет — прямой доступ не даёт заголовков.
Поэтому при выключенной авторизации доступ не режется: иначе включённый RBAC без
входа запер бы всех.

### Имена групп сверяются точно

Регистр и ведущий слэш значимы: Keycloak часто отдаёт `/team-oncall`, а не
`team-oncall`. Фактически приходящие строки видны в `GET /access/me`, поле
`groups`. Разбор у всех переменных общий (`access._groups_of_var`): деление по
запятой, обрезка пробелов.

## Двойная защита

**Бэкенд.** На роутер модуля вешается зависимость — 403 на любой его роут:

```python
router = APIRouter(
    prefix="/victoria",
    dependencies=[Depends(require_module("victoria"))],
)
```

**Фронт.** `App.vue` читает `GET /access/me` и показывает в рельсе только
доступные вкладки. Активная вкладка автоматически переключается на первую
доступную; если доступных нет — вместо пустого экрана выводится сообщение
«Нет доступа».

Если `/access/me` недоступен, фронт показывает все вкладки — но их API всё равно
вернёт 403, поэтому защита не ослабевает.

## Новый модуль

Id модуля добавляется в `KNOWN_MODULES` в `backend/access.py`. Без этого
`/access/me` не вернёт модуль в списке, и вкладка не появится при включённом
RBAC — даже если API модуля работает.

## Диагностика

### `GET /access/debug`

Показывает, что **реально дошло** до бэкенда: заголовки `X-Forwarded-*` (токены
— только размером), размеры cookie, действующая конфигурация и поле `hint` с
подсказкой, на каком хопе искать потерю.

### `GET /access/me`

Итоговое решение: имя, группы, признак админа, список доступных модулей,
таймзона показа дат.

### Логи

| Событие | Когда | На что смотреть |
| --- | --- | --- |
| `auth.config` | при старте | действующие `AUTH_*` и `RBAC_*`, поле `rbac_active` |
| `auth.me` | запрос `/access/me` | какие группы и модули получил пользователь |
| `auth.no_username_header` | `AUTH_ENABLED=true`, а имя не пришло | это и есть «постоянно local» |
| `auth.denied` | RBAC не пустил | модуль, пользователь, его группы |

Access-лог nginx фронта (`authlog`) показывает, что пришло от oauth2-proxy.
Сопоставление двух логов локализует потерю:

- в `authlog` имя есть, а бэкенд пишет `local` → теряется на хопе nginx → бэкенд;
- в `authlog` имя пустое → теряется раньше: oauth2-proxy или внешний nginx.

Подробности по логам — [LOGGING.md](LOGGING.md).

## Типовые причины «вечного local»

| Причина | Как проверить |
| --- | --- |
| `AUTH_ENABLED=false` в окружении контейнера | событие `auth.config` при старте |
| Внешний nginx не проставляет личность в конкретном `location` | заголовки в `/access/debug` |
| Заголовки не пережили хоп: крупные cookie и группы превысили буферы | `cookie_bytes` и `groups_bytes` в `/access/debug` |
| У прокси другое имя заголовка | сравнить `user_header` из `/access/debug` с реальным |

Личность проставляется **в каждом `location`** внешнего nginx, а не только в
корневом: пропущенный блок даёт запросы без имени именно на своих путях.
Буферы под крупные заголовки описаны в [NGINX.md](NGINX.md).
