# Архитектура dev-tool

Модульный веб-инструмент для эксплуатации observability-контура. Одно
приложение, несколько независимых модулей.

**Основной принцип: 1 модуль = 1 роутер на бэкенде = 1 вкладка во фронте.**

Стек: **backend** — FastAPI (Python), **frontend** — Vue 3 + Vite. Сервисы
собираются и выкатываются независимо друг от друга.

---

## Общая схема

```
                    ┌─────────────────────────────────────────┐
   браузер ────────►│ внешний nginx (TLS, имя хоста)          │
                    │   └─ auth_request → oauth2-proxy         │
                    └───────────────────┬─────────────────────┘
                                        │ + X-Forwarded-Preferred-Username
                                        │ + X-Forwarded-Groups
                    ┌───────────────────▼─────────────────────┐
                    │ frontend: nginx + собранная статика Vue │
                    │   /            → SPA                    │
                    │   /silences/   ┐                        │
                    │   /victoria/   ├─► backend_pool         │
                    │   /alerts/     │   (least_conn, HA)     │
                    │   /access/     │                        │
                    │   /share, /s/  ┘                        │
                    │   /webhook/    ─► n8n                   │
                    └───────────────────┬─────────────────────┘
                                        │
                    ┌───────────────────▼─────────────────────┐
                    │ backend: FastAPI                        │
                    │   access.py  — RBAC, /access/me         │
                    │   share.py   — короткие ссылки          │
                    │   modules/silences  ─► Alertmanager     │
                    │   modules/victoria  ─► vmselect/vmagent │
                    │   modules/alerts    ─► Postgres         │
                    └───────────────────┬─────────────────────┘
                                        │
                        ┌───────────────┴───────────────┐
                        ▼                               ▼
                 Postgres или диск             внешние системы
                 (правила, история,            (Alertmanager, VM,
                  короткие ссылки)              Prometheus, n8n)
```

Браузер обращается только к фронту. Бэкенд наружу открывать не требуется:
внутренний nginx проксирует к нему все API-пути. Подробности маршрутизации —
[NGINX.md](NGINX.md).

## Устройство модуля

### Бэкенд

Папка `backend/modules/<имя>/` отдаёт `router` — FastAPI `APIRouter` с префиксом
`/<имя>`. Подключается одной строкой в `backend/main.py`:

```python
from modules.<имя>.routes import router as <имя>_router
app.include_router(<имя>_router)
```

Типовой состав модуля:

| Файл | Назначение |
| --- | --- |
| `config.py` | чтение своих переменных окружения при импорте |
| `client.py` | HTTP-клиент к внешней системе (`httpx`, `trust_env=False`) |
| `deps.py` | мелкие проверки-зависимости, например `require_env` |
| `routes.py` | сам роутер, на него вешается `require_module("<имя>")` |
| `storage.py` | работа с хранилищем, если модулю нужны свои данные |

### Фронтенд

Папка `frontend/src/modules/<имя>/` с файлом-дескриптором `index.js`:

```js
export default {
  id: 'victoria',            // = id модуля в RBAC
  title: 'Victoria Metrics',
  subtitle: 'Query, Targets, Rules',
  icon: 'M3 3v18h18…',       // значение атрибута d у <path> иконки
  component: VictoriaModule, // корневой .vue модуля
}
```

Регистрируется одной строкой в `frontend/src/modules/registry.js`. Левый рельс
иконок и переключение вкладок в `App.vue` строятся из этого реестра.

Все запросы модуля собраны в его `api.js` и идут относительными путями
(`/victoria/…`). Проксирование выполняет Vite при разработке и nginx в
собранном образе.

Инструкция на добавление модуля — [MODULES.md](MODULES.md).

## Модули

### silences — вкладка «Silence Manager»

Управление silence в Alertmanager: разовые по датам и повторяющиеся по
расписанию (сетка дни × часы + минуты).

- **источник правды — хранилище правил, а не Alertmanager**: список и статус
  считаются по своим данным, в AM правила только применяются;
- шедулер раз в `SILENCE_CRON` синхронизирует хранилище и доставляет
  недостающие silence — например, если AM был недоступен в момент создания;
- при создании правила с теми же матчерами и концом алертинга запрос
  блокируется кодом 409 с именем существующего правила;
- удалённое правило не стирается, а переносится в `<env>/old/…` (либо
  помечается `deleted_at`) — из интерфейса пропадает, в истории остаётся;
- атрибуция «кто что сделал» пишется полем `user` в журнале истории.

Окружения задаются переменными `alert_<env>` (обязательна минимум одна) и
`rules_<env>` (источник определений алертов — Prometheus или vmalert).

**Инвариант — ломать нельзя:** интерфейс задаёт и показывает «настенное» время в
`SILENCE_TZ`, а Alertmanager работает в UTC. Перевод делает `am_format.to_am_time()`:
он локализует naive-datetime в `SILENCE_TZ` **перед** переводом в UTC. Без этого
шага `naive.astimezone()` берёт таймзону контейнера, и silence уезжает на
несколько часов. На фронте `shared/time.js` зеркалит правило: строки с зоной
(из Alertmanager, из истории) переводятся в `SILENCE_TZ`, naive-строки из полей
`datetime-local` показываются как есть.

Роуты: `/silences/environments`, `/silences/me`, `/silences/{env}/rules`,
`/silences/{env}/alerts`, `/silences/{env}/history`,
`/silences/{env}/rules/{kind}/{id}` (PUT/DELETE, enable/disable),
`/silences/{env}/manual`, `/silences/{env}/schedule` (+ `/preview`).

### victoria — вкладка «Victoria Metrics»

Тонкий прокси к кластерам VictoriaMetrics: фронт запрашивает данные у бэкенда,
бэкенд обращается к нужному компоненту кластера и возвращает его ответ. У
vmselect API совместим с Prometheus, поэтому разбор на фронте — обычный
Prometheus-формат.

Кластер описывается переменными окружения, имя `<env>` после префикса
становится названием вкладки:

| Переменная | Обязательна | Что включает |
| --- | :---: | --- |
| `vm_<env>` | да | vmselect → под-вкладки **Graph** и **TSDB Status** |
| `vmagent_<env>` | нет | vmagent → под-вкладка **Targets** |
| `vmalert_<env>` | нет | vmalert → под-вкладка **Rules** |

Кластер только под хранение описывается одной переменной `vm_<env>` —
под-вкладки Targets и Rules у него не появятся. Несколько нод компонента (HA)
перечисляются через запятую, чтение идёт с первой живой.

| Под-вкладка | Компонент фронта | Роут бэкенда |
| --- | --- | --- |
| Graph | `QueryPanel.vue` | `/{env}/query`, `/{env}/query_range`, `/{env}/labels`, `/{env}/label_values` |
| Targets | `TargetsList.vue` | `/{env}/targets` |
| Rules | `RulesAlerts.vue` | `/{env}/rules`, `/{env}/alerts` |
| TSDB Status | `Cardinality.vue` | `/{env}/tsdb` |
| Disk Usage | `DiskUsage.vue` | `/disk-usage` — сводно по всем кластерам |

Мультитенантность поддерживается синтаксисом `vm_<cluster>__<подпись>=<URL с
нужным accountID в пути>`: кластер становится одной вкладкой с селектором
тенанта. Тенант влияет только на чтение метрик; `vmagent_`/`vmalert_` общие на
кластер.

**Инварианты — ломать нельзя:**

- **ось X графика строится на весь запрошенный период**, точки ответа кладутся в
  ближайший слот сетки, серии рисуются с `spanGaps: false`. Если строить ось по
  крайним точкам ответа, метрика, переставшая идти неделю назад, дотянется линией
  до правого края и будет выглядеть живой;
- **тултип не выбирает серии, скрытые в легенде**, и меряет расстояние до самой
  линии, а не по вертикали в точке: иначе наводишься на одну линию, а в окошке
  оказывается другая метрика;
- **ответы VM проходят сырыми байтами** (`Response`), без разбора и пересборки
  JSON. Исключение — targets, их специально облегчают;
- **`query` и `query_range` не кэшируются** — это живые данные, и их уже
  ускоряет rollup-кэш самой VM. Кэшируются только targets, tsdb, имена
  метрик/лейблов и rules;
- **под-вкладки обёрнуты в `KeepAlive`**: переключение вкладки не пересоздаёт
  компонент и не перечитывает данные. Смена кластера или тенанта пересоздаёт
  (через `:key`).

### alerts — вкладка «Alert Constructor»

Конструктор алертов поверх Elasticsearch-индексов. Конфигурации ведёт **n8n** —
он остаётся source of truth; фронт обращается к нему по пути `/webhook/…`,
который внутренний nginx проксирует на `N8N_URL`.

Бэкенд хранит в Postgres метаданные: журнал изменений, статус backend-workflow и
зеркало конфигов для мгновенной отрисовки интерфейса после перезагрузки
страницы.

| Роут | Назначение |
| --- | --- |
| `GET /alerts/cache` | полный кэш для гидрации UI: `alerts`, `engine`, `indexPatterns` |
| `PUT /alerts/cache` | обновление кэша после успешного чтения из n8n |
| `GET/PUT /alerts/engine` | heartbeat backend-workflow: `lastRunAt`, `lastError` |
| `GET/POST /alerts/history` | журнал create/update/delete |
| `POST /alerts/fields` | поля индекса: Postgres TTL-кэш → n8n/ELK |
| `POST /alerts/indices` | паттерны индексов: Postgres TTL-кэш → n8n/ELK |

Таблицы `alerts_history`, `alerts_meta`, `alerts_configs` описаны в
[STORAGE.md](STORAGE.md). Без настроенного Postgres модуль работает, теряя
только историю и кэш. Lookup `fields`/`indices` при недоступном Postgres
каждый раз ходит в n8n (деградация без отказа).

## Общие механизмы

### Состояние вида в URL и короткие ссылки

Состояние страницы хранится в query-параметрах URL и обновляется на лету через
`history.replaceState` (`frontend/src/shared/urlstate.js`):

| Параметр | Кто пишет | Смысл |
| --- | --- | --- |
| `m` | `App.vue` | активный модуль |
| `env`, `tab` | каждый модуль | окружение и под-вкладка |
| `tenant` | victoria | выбранный тенант |
| `q` (несколько), `mode`, `from`, `to`, `eval` | victoria | запросы, режим и период |

Такую ссылку можно передать коллеге — откроется тот же вид, запросы выполнятся
сами. Смена кластера или тенанта очищает параметры запроса.

Кнопка «ссылка» в шапке укорачивает адрес: `POST /share {path}` сохраняет путь и
возвращает `id = sha256(path)[:8]`, `GET /s/<id>` отвечает редиректом 302.
Принимаются только относительные пути (`/…`, не `//…`) — защита от open redirect.

### Авторизация и доступ к вкладкам

Личность и группы приходят от oauth2-proxy заголовками
`X-Forwarded-Preferred-Username` и `X-Forwarded-Groups`. Права выдаются на
модуль целиком переменными `access_<module>` и `RBAC_ADMIN_GROUP`. Защита
двойная: бэкенд отвечает 403 на API чужого модуля, фронт прячет вкладку.
Подробно — [RBAC.md](RBAC.md).

### Хранилище

Два режима, переключаются `STORAGE_BACKEND`: `local` (файлы на диске, одна нода)
или `postgres` (общая БД, сколько угодно нод, шедулер координируется
advisory-локом). Подробно — [STORAGE.md](STORAGE.md).

### Логи

Оба сервиса пишут NDJSON в stdout: бэкенд — события приложения и ошибки
запросов, nginx фронта — access-лог с личностью. Подробно —
[LOGGING.md](LOGGING.md).

### Тема и цвет-пространство

Активная вкладка задаёт `data-space` на `<html>`, и палитра перекрашивается
целиком — модуль ощущается отдельным местом. Светлая и тёмная темы
переключаются `data-theme`. Подробно — [UI.md](UI.md).
